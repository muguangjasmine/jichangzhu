# 节点延迟高或全部超时？连通性排查与切换建议

打开客户端节点列表，执行全员测速后发现平时几十毫秒的绿色节点全部飙升至数百毫秒，甚至大面积显示为红色的“Timeout（超时）”，是很多代理用户最为头疼的时刻。节点延迟的高低与连通性不仅受服务商机房状态影响，还与本地网络路由、国际海缆状况及协议配置密切相关。系统性地排查延迟异常，能让你在最短时间内恢复敏捷的网络响应。

## 延迟高与超时的三类本质原因

在采取解决行动前，首先需区分异常发生的范围：
1. **单点高延迟（个别节点变红）：** 属于机房局部硬件重启、网络单线波动或该节点正在进行临时出口维护，属于正常偶发事件；
2. **全员大面积超时（所有节点全红）：** 通常是本地环境问题（系统时间偏差、本地断网、客户端内核挂死）或服务商的国内入口服务器突遭阻断；
3. **整体延迟上浮（原本50ms变成300ms）：** 通常属于国际光缆故障导致服务商临时启用了远距离绕路备用线路。

## 第一步：重启客户端内核并排查本地基础链路

很多时候由于电脑休眠唤醒或长时间运行，底层的内核进程可能出现假死：
1. 在 Clash Verge Rev 界面右上角，点击小刷新图标重启内核核心；
2. 检查本地电脑连接的基础 WiFi 是否正常，先打开一个普通的国内网站确认本地原生网络没有欠费断开；
3. 打开命令行窗口（CMD），输入 `ping 223.5.5.5`，观察本地网关到公共 DNS 的往返延迟是否稳定在 30ms 以内，排除本地 WiFi 严重丢包。

## 第二步：掌握正确的“节点测速（Ping）”测试方法

客户端内的测试方式会直接影响测速结果：
- **TCP 握手测速（RTT）：** 仅测试本地到代理服务器入口机房的 TCP 握手时长，数值通常极低，但不能完全反映网页真实打得开；
- **HTTP / URL-Test 真实连通测速：** 模拟向目标服务器（如 `www.gstatic.com/generate_204`）发送真实请求。如果显示超时，说明该节点虽然能通达入口，但境外落地出口已经失效；
- **切换测速源：** 在客户端设置中，将测速 URL 修改为国内与国际通达性较好的标准 204 站点，避免由于特定测试服务器宕机导致的全员误报超时。

## 第三步：低延迟节点的优选切换策略

当常用香港节点出现延迟剧烈抖动时，不要盲目乱点：
- **第一备选梯队：日本东京机房节点（JP）**  
  日本节点拥有极高的国际带宽容灾能力，延迟通常在 45ms 至 75ms 之间，几乎是香港节点遇到波动时的完美第一替代者；
- **第二备选梯队：新加坡核心节点（SG）**  
  作为亚太区域的核心中继，抗抖动能力极佳；
- **避坑提示：** 切勿直接切换至欧美节点来解决延迟问题。由于横跨太平洋和大西洋的物理光速极限，美国节点延迟不可能低于 130ms，不适合用于追求低延迟的即时网页浏览。

## 节点延迟异常分类与处理指南表

| 故障表象 | 核心原因诊断 | 推荐处理策略 |
| :--- | :--- | :--- |
| **全部节点整齐显示 Timeout** | 本地系统时间不同步或代理内核假死 | 同步 Windows 时间，重启客户端内核 |
| **仅香港节点超时，日本正常** | 香港机房临时出口维护或阻断 | 在代理分组中切换至日本或新加坡节点备用 |
| **所有节点延迟均翻倍飙升** | 国际海缆突发故障导致运营商借道绕路 | 关注机场官方维护公告，耐心等待路由修复 |
| **测速显示延迟但网页打不开** | 浏览器存在扩展冲突或 DNS 污染 | 清除浏览器缓存，修复本地 DNS 设置 |

## 节点延迟常见问答

**Q：为什么客户端测出来的延迟是 30ms，但打开网页依然感觉有点卡？**  
A：客户端测试的仅仅是连接代理服务器的往返延迟（Ping）。如果目标海外网站本身的服务器负载极重，或者该代理节点分配的即时带宽已被其他用户占满，依然会出现加载停顿。

**Q：长期挂在“自动选择（Auto/URL-Test）”策略组好不好？**  
A：对于优质专线机场，自动选择策略组非常省心，能自动屏蔽超时节点；但对于波动较大的机场，频繁自动切换可能导致你的登录 IP 频繁变动，触发某些网站的安全验证。
